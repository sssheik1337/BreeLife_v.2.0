# Acceptance baseline для миграции legacy → SPA

Документ фиксирует обязательные сценарии проверки паритета перед отключением legacy-страниц.

## Цель baseline

- Подтвердить отсутствие функциональной и визуальной деградации при миграции на SPA.
- Зафиксировать единый список сценариев и критериев прохождения (go/no-go).
- Запретить отключение legacy, пока не достигнут 100% паритет по критичным сценариям.

## Формат проверки сценариев

Для каждого сценария фиксируются:

1. **Ожидаемый маршрут** (URL и редиректы).
2. **Ожидаемые API-вызовы** (минимум ключевые endpoint’ы).
3. **Ключевые UI-состояния** (данные, блоки, состояния загрузки/ошибок).
4. **Анимации** (что должно отрабатывать и без изменения контракта duration/easing).
5. **Статус паритета**: `PASS / FAIL`.

## Список пользовательских сценариев

### S1. Авторизация и вход в приложение

- **Ожидаемый маршрут:** `/` → (после успешной авторизации) `/profile` или `/questionnaire` по состоянию профиля.
- **API-вызовы:** `/api/app/config`, `/api/me/status`.
- **Ключевые UI-состояния:**
  - корректная инициализация Telegram WebApp;
  - отображение приветствия/первичного экрана;
  - корректная обработка неавторизованного состояния.
- **Анимации:** базовый page transition (`fadeIn`/переход страницы).
- **Статус паритета:** TBD.

### S2. Анкета (`questionnaire`)

- **Ожидаемый маршрут:** `/questionnaire` → `/preferences-onboarding-choice` или `/trial-start` (по `preferences_onboarding_completed`).
- **API-вызовы:** `/api/me/status`, `/api/profile`, `/api/profile/save`.
- **Ключевые UI-состояния:**
  - шаги анкеты и прогрессбар;
  - валидация полей;
  - сохранение в профиль без потери уже введённых значений.
- **Анимации:** переходы между шагами анкеты, page transition.
- **Статус паритета:** TBD.

### S3. Онбординг предпочтений (`preferences-onboarding*`, `trial-start`)

- **Ожидаемый маршрут:**
  - `/preferences-onboarding-choice` (если профиль завершён);
  - `/trial-start` только по правилу `should_redirect_to_trial_start`;
  - редиректы в `/questionnaire` при незавершённом профиле.
- **API-вызовы:** `/api/profile`, `/api/profile/save`, `/api/me/status`.
- **Ключевые UI-состояния:**
  - выбор сценария онбординга;
  - корректное сохранение product-preferences;
  - отсутствие циклических редиректов.
- **Анимации:** page transition и вход/выход блоков онбординга.
- **Статус паритета:** TBD.

### S4. Дневник (`diary`) — критичный экран

- **Ожидаемый маршрут:** `/diary` (доступ только после завершения профиля).
- **API-вызовы:** `/api/diary`, `/api/diary/save`, `/api/habits`, `/api/habits/save` (или канонические эквиваленты из контракта).
- **Ключевые UI-состояния:**
  - карточки прогресса/приёмов пищи;
  - water/sleep/habits;
  - корректная работа FAB и панелей;
  - отсутствие потери данных при обновлении/сохранении.
- **Анимации:** `diary-panel-in`, `diary-fab-in`, ripple, page transition.
- **Статус паритета:** TBD.

### S5. Рацион (`meal-plan`) и покупки (`shopping-list`)

- **Ожидаемый маршрут:** `/meal-plan`, `/shopping-list` с guard на product onboarding.
- **API-вызовы:** `/api/meal-plan/day`, `/api/meal-plan/week`, `/api/profile`.
- **Ключевые UI-состояния:**
  - загрузка дневного/недельного плана;

  - редирект в `/preferences-onboarding` при отсутствии продуктовых данных.
- **Анимации:** page transition, shimmer/skeleton (если используется).

## Чек "pixel/behavior parity" для критичных экранов

Критичные экраны: **`diary`, `profile`, `resume`**.

Для каждого экрана обязательны:

1. **Pixel parity:**
   - визуальная сверка legacy vs SPA в одинаковых состояниях (до/после действий);
   - проверка отступов safe-area/header/footer;
   - проверка типографики, размеров карточек, позиционирования CTA/FAB.
2. **Behavior parity:**
   - идентичные редиректы и guard-правила;
   - идентичный порядок загрузки/обновления данных;
   - отсутствие новых race-condition/миганий/скачков layout.
3. **Animation parity:**
   - неизменные `duration` и `timing-function` до окончания миграции;
   - совпадение сценариев появления/скрытия панелей и интерактивных элементов.

Статус фиксируется отдельно для каждого экрана: `PASS / FAIL`.

## Матрица устройств/режимов

Проверки baseline выполняются минимум в следующих средах:

| Платформа | Режим | Обязательные проверки |
|---|---|---|
| Telegram iOS | WebApp (fullscreen + non-fullscreen) | Safe-area, header offset, viewport changes, стабильность анимаций |
| Telegram Android | WebApp | Паритет маршрутов, FAB/panel анимации, стабильность скролла |
| Telegram Desktop | WebApp | Навигация, адаптивность, корректность layout и переходов |

Каждый критичный сценарий (`S4`, `S6`) должен быть пройден на всех трёх платформах.

---

## Критерий отключения legacy

**Legacy-слой можно отключать только при условии 100% прохождения baseline по всем критичным сценариям.**

Минимальные требования:

1. `S4 (diary)` = PASS на iOS/Android/Desktop.
2. `S6 (profile/resume)` = PASS на iOS/Android/Desktop.
3. Нет открытых P1/P0 дефектов по маршрутам, данным и анимациям.
4. Feature-flag rollback протестирован и подтверждён.

При любом FAIL: отключение legacy блокируется до устранения причины и повторного прогона baseline.
